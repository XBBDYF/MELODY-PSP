# 能不能做一个「极其省电」的主题？——可行性验证

> 结论先说：**纯主题做不到「极其省电」；能做到的是「主题少干活」，再配合一个很小的 C 级省电模式，才有可观的续航收益。**
> 本文给出代码证据、可测指标和已经准备好的验证工具，避免凭感觉下结论。

---

## 1. PSP 的功耗花在哪

| 部件 | 是否能被主题影响 | 说明 |
|---|---|---|
| LCD 背光 | **不能** | PSP 是 LCD，背光常亮；**深色/黑色主题不会省电**（OLED 才成立），亮度只能用户手动调 |
| SoC 时钟 | **不能**（主题 API 里没有） | 程序没有调用 `scePowerSetClockFrequency`；实测运行在 **333MHz / bus 166MHz** |
| CPU 每帧绘制 | **能，部分** | 主题决定每帧画多少东西；但程序固定 60fps 全屏重绘 |
| Wi-Fi | **不能**（主题 API 里没有） | 在线播放/下载时功耗显著；断开需要 C 级动作 |
| 记忆棒读取 | **能，部分** | 主题可以不带图片/字体、不每帧读封面 |
| 音频解码/功放 | **不能** | 播放时一直在跑，和主题无关 |

---

## 2. 代码审计（有出处的事实）

1. **主循环每帧都重画**：`main.c` 的 `while (running)` 里每轮执行 `ui_draw()` → `gfx_flip()`；
2. **帧率被垂直同步锁在 60fps**：`gfx.c:gfx_flip()` 里 `sceDisplayWaitVblankStart()`；
3. **画面不变也照画**：没有脏矩形/跳过逻辑；
4. **CPU 渲染路径每帧拷 278KB**：`gfx.c` 注释写明「正常 UI 在 RAM 绘制，复制到 VRAM；278KB memcpy」，
   并调用 `sceKernelDcacheWritebackRange`；
5. **可以切 GE 渲染**：`gfx.c:gfx_set_renderer()` 支持 GPU 列表渲染，能减少 CPU 填充；
6. **程序没有主动设置时钟**：全仓库 `grep scePowerSetClockFrequency` 无结果；
   `main.c` 只读取并打印 `clock=333MHz bus=166MHz`；
7. **主题侧 API 没有时钟/背光/帧率控制**：`ui.*` / `app.*` 全表里没有相关函数；
8. **主题能省的只有「每帧绘制量」**：填充次数、文字行数、渐变/遮罩面积、封面/唱片绘制、图片解码。

---

## 3. 三档方案与收益

| 方案 | 改动 | 预计收益 | 结论 |
|---|---|---|---|
| A. 纯主题（只改 `skin.json` / `skin.lua`） | 主题作者自己做 | 「每帧 CPU 时间」可降 50–80%（取决于原主题多花哨）；**整机续航通常只有个位数百分比** | 做不到「极其省电」 |
| B. 主题 + 省电模式（小改 C） | 时钟降频 + 静帧跳过 + 空闲断网 | 菜单/歌词页 **约 20–35%**（估算），本地播放 **10–20%** | 可行，收益主要来自这里 |
| C. 想「续航翻倍」 | 硬件/背光 | 软件达不到 | 不现实 |

> 收益百分比是**估算**，本文第 5 节的工具就是为了把它变成实测数字。

## 4. 省电模式该怎么写（草案）

```c
/* 设置项「省电模式」打开时 */
scePowerSetClockFrequency(222, 222, 111);   /* MV 播放/解码时自动恢复 333 */
```

```c
/* 静帧跳过：画面没变化就不重画（保留 flip 以维持扫描输出） */
if (!ui_dirty() && !skin_transition_active() && !g_anim_active) {
    gfx_flip();
    sceKernelDelayThread(16 * 1000);
} else {
    ui_draw();
    gfx_flip();
}
```

```c
/* 空闲断网：不在播放/下载且 60 秒无操作 */
if (!audio_streaming() && !dl_active() && idle_seconds() > 60)
    sceNetApctlDisconnect();
```

风险与边界：

- MV 硬件解码对时钟敏感，**MV 播放时必须恢复 333MHz**；
- 30fps 上限对滚动列表手感有影响，建议只在「静态页」启用；
- 断网后再次联网需要重新 `sceNetApctlConnect`，要避免在播放中误断。

## 5. 已经准备好的验证工具

### 5.1 埋点（已编译进测试固件）

每 300 帧输出一行：

```text
perf: draw_us=<UI绘制耗时> flip_wait_us=<等垂直同步的空闲时间> frames=300 screen=<页面号>
```

- `draw_us` 与 CPU 功耗正相关，是主题能影响的量；
- `flip_wait_us` 大说明 CPU 有大量空闲，此时**降频的收益更直接**；
- 日志写到程序目录 `log.txt`。

### 5.2 ECO 原型主题

`THEME-KIT/EXAMPLES/eco/`：整屏 1 个矩形 + 每页最多 4 行文字，无封面、无渐变、无动画、无音效、无字体。
已通过 `check_skin.py` 与真运行时校验（VALID）。

### 5.3 已经测到的一个基线数（PPSSPP）

启动/WiFi 页上（两套主题都回落原生界面，所以这里测的是**基线绘制成本**）：

```text
perf: draw_us=2562 flip_wait_us=12790 frames=300 screen=1   (metro)
perf: draw_us=3139 flip_wait_us=12157 frames=300 screen=1   (eco)
```

一帧 15.7ms（60fps）里：
- 原生 UI 绘制约 **2.5–3.5ms**（16–22% 的 CPU 时间）；
- 其余 **12.2–12.8ms** 在等垂直同步（空闲）。

这说明两件事：
1. 即使把主题绘制压到 0，也只能影响这一小段（而背光/音频照旧耗电）→ 纯主题省不出「极其省电」；
2. `flip_wait_us` 这么大，说明**降频/静帧跳过**有空间——这正是省电模式的价值。

### 5.4 测量步骤

1. 把测试固件 `melody.prx` 和 `eco/` 装进卡；
2. 电量充满（或记下起始百分比与 `scePowerGetBatteryElec`）；
3. 选 `metro`，进播放页，播放同一首本地歌，**静置 10 分钟**，记录 `perf:` 行与结束电量；
4. 换 `eco`，重复同样 10 分钟；
5. 对比：`draw_us` 比值、10 分钟掉电百分比、`flip_wait_us`。

判据：

- 如果 `eco` 的 `draw_us` 只有 `metro` 的 1/3 以下 → 主题侧确实还有可观 CPU 节省空间；
- 如果两者 `draw_us` 都很小（例如 < 1ms）而 `flip_wait_us` 很大 → **主题不是瓶颈**，收益必须来自降频/静帧跳过/断网，即方案 B。

### 5.5 电池测量的注意点

- PSP 电量百分比是 1% 粒度，10 分钟可能只掉 1–2%，**建议每次 30–60 分钟**；
- 更细的读数用 `scePowerGetBatteryElec()`（mAh 级别，视固件支持）；
- 两次测量要同样的音量、亮度、耳机/外放、是否插卡、是否联网。

---

## 6. 当前判定

1. **「极其省电的主题」不存在**——主题碰不到背光、时钟、Wi-Fi、音频这四块大头；
2. **「明显更省电的主题 + 省电模式」可行**，改动量小（一个设置项 + 三处逻辑）；
3. 真正决定收益的是 **CPU 忙等时间**：60fps 全屏重绘 + 278KB 帧拷贝是现状；
   省电模式把「静态页」的这部分几乎清零，这才是续航提升的来源。

---

## 7. 下一步（按收益排序）

1. 先跑第 5 节的对照测量，拿到 `draw_us` 与掉电数据（1 小时，两次）；
2. 若 `draw_us` 占比高 → 先做**静帧跳过 + 30fps 静态页**（纯 C，收益最大且不影响音质）；
3. 再做**省电模式设置项**（222MHz，MV 自动恢复）；
4. 最后做**空闲断网**（需处理重连）；
5. 主题侧把 ECO 的做法写进 THEME-KIT（少填充、不逐帧动画、不带图），作为「轻量主题」规范。
